# Первое игровое испытание AI Companion

Дата: 30.10.2026  
Сценарий: `spawn → follow → stay → follow → dismiss`  
Среда: только LOCAL-мир `AI Body Test`, slot 1, и LOCAL-персонаж `Body Test`, slot 1.

## Текущее состояние

Испытание завершено безопасной остановкой. Runtime preflight прошёл, однако единственный подтверждённый `spawn` завершился `fingerprint_missing`; созданный Vukah остался враждебным и убил тестового персонажа. Остальные команды заблокированы. После закрытия игры пользователь отдельно подтвердил offline-восстановление, и тестовый LOCAL-набор полностью возвращён к pre-spawn состоянию.

## Журнал игровых команд

### spawn

- Время: 30.10.2026 19:55:10 UTC.
- Request ID: `stage5-spawn-20261030T1956Z`.
- Epoch: `895d68a8425ad96d-1-table000001A9B2792FF00001000000`.
- Запрос: `action=spawn`, постоянный companion ID из локального профиля, проверенные LOCAL world/character slot 1. Отправлен ровно один раз через Python CLI.
- Ответ: `status=failed`, `phase=failed`, `code=fingerprint_missing`, `state_confirmed=false`, `event_submission=not_requested`.
- Состояние до: `mode=absent`, без recovery/orphaned/uncertain spawn.
- Состояние после: entity ID 6854, `body_trusted=false`, `mode=recovery_required`, `recovery_required=true`, `uncertain_spawn=false`, `recovery_action=dismiss`.
- Защитный `runtime.lock` существует, содержит формат v2 и текущий epoch. Он не изменялся и не удалялся вручную.
- Read-only status по тому же request ID подтвердил тот же окончательный результат. Повторный spawn не выполнялся.
- Визуальный результат: пользователь подтвердил появление враждебного NPC. NPC атаковал и убил персонажа; персонаж возродился. Присланный скриншот показывает крупного Vukah первого уровня вплотную к персонажу, с красной полосой здоровья и враждебным индикатором. Служебная бочка в кадре не видна. Сам скриншот в репозиторий не добавляется.
- Read-only status после возрождения подтвердил прежний failed request и состояние recovery на tick 12617.
- `dismiss` не отправлялся: fingerprint отсутствует, поэтому адаптер не имеет права уничтожать тело по этому ID. После перемещения игрока вследствие смерти одно лишь исчезновение ID из активного ECS также не докажет очистку сохранения.

Полные runtime-логи и персональные пути в Git не публикуются.

## Подтверждённые функции и ошибки

- Подтверждено, что Bridge принял структурированный запрос и `emf.spawn` вернул entity ID.
- Получение fingerprint созданной сущности не сработало: `fingerprint_missing`. Поэтому faction, health и готовность тела не подтверждены. Фактическое поведение оказалось враждебным: NPC атаковал и убил игрока.
- Защита адаптера сработала: сущность не объявлена доверенной, включён recovery, новый spawn/follow/stay заблокированы, lock сохранён.
- Полный сценарий неуспешен; `follow`, `stay`, повторный `follow` и полноценный `dismiss` заблокированы. Безопасный следующий шаг — закрыть игру и, только после отдельного разрешения, восстановить тестовые LOCAL character/world из проверенной pre-spawn копии. Исправления кода до фиксации результата не вносятся.

## Состояние после остановки игры

- Пользователь штатно закрыл Enshrouded; процессы клиента и dedicated server отсутствуют.
- От pre-spawn копии отличаются четыре существовавших файла тестового LOCAL-набора: `character0.ksd`, `world0.ksd` и две последние ротационные копии мира.
- Игра создала четыре новые ротационные копии `character0.ksd`, которых не было в pre-spawn manifest.
- Текущие восемь тестовых файлов и защитный lock сохранены как диагностический снимок в игнорируемом Git каталоге `runtime/recovery/stage5-failed-20261030T1958Z`; 9/9 хешей повторно проверены, ошибок 0.
- Пользователь отдельно подтвердил offline-восстановление. Первая попытка безопасно остановилась после замены четырёх основных файлов из-за лишнего уровня `default` в проверке пути диагностической копии; новые backup-файлы и lock при этом не изменились. После исправления только этой проверки операция продолжена идемпотентно.
- Восстановлены четыре изменённых файла, удалены четыре созданные тестом ротационные копии персонажа. Все 19 файлов LOCAL-набора совпали с pre-spawn manifest, ошибок и лишних файлов 0.
- После полной сверки активный `runtime.lock` перемещён в диагностический архив; он не удалён. Основные и Steam-backed сохранения не изменялись.

## Итог и следующий этап

Действительно подтверждено:

- Python Bridge принимает структурированные запросы в запущенном LOCAL-мире.
- EMF 0.3.2 загружает Lua 1.9.0 и `aic_body` 0.1.0 на build 1273043.
- `emf.spawn` создаёт `Enemy_Vukah_Melee` и возвращает ненулевой entity ID.
- Защита от повторного spawn, недоверенного удаления и потери lock сработала; восстановление из pre-spawn копии вернуло тестовый набор в исходное состояние.

Не сработало или не было проверено:

- Сразу после spawn `inspect()` не дал обязательный fingerprint. Код ответа не различает, отсутствовал ли `ModelResource`, `kind` либо весь снимок; по текущей реализации наиболее точный подтверждённый вывод — `fingerprint_missing`.
- Из-за отказа fingerprint код не дошёл до `ally()`: faction 11 не устанавливалась. NPC остался враждебным и убил игрока.
- Guard/follow не отправлялся (`event_submission=not_requested`). `follow`, `stay`, повторный `follow`, маркер и штатный `dismiss` не проверены.
- Health, ready-флаг, длительное следование, навигация и полная live-очистка NPC не подтверждены.

Перед повторным игровым испытанием Body Adapter требует отдельного исправления и ревью:

1. Добавить безопасную диагностику причины неполного fingerprint без повышения доверия к сущности.
2. Найти подтверждённый доступный fingerprint для экземпляра `Enemy_Vukah_Melee` на build 1273043 либо признать этот body template несовместимым с текущей моделью идентичности.
3. Исключить появление активного враждебного NPC при отказе fingerprint. Решение должно опираться на подтверждённый EMF API и сохранять запрет удаления по неподтверждённому ID; просто переставить небезопасную запись faction до проверки идентичности нельзя без отдельного анализа.
4. Повторить тест только в восстановленном LOCAL-мире с новой резервной копией и новым отдельным подтверждением.

Переходить к Brain, голосу, памяти или навыкам пока нельзя. Следующий этап — исправление Body Adapter на основании этого фактического результата.
