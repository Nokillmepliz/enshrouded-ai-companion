# План проверки тела

Статус: **игровые испытания не проводились**. В этом этапе запускаются только тесты проекта без игры. Установка и все пункты игрового раздела ждут подтверждения пользователя.

## Автоматические тесты без игры

Команда: `python -m unittest discover -s tests -v` после установки `requirements-test.txt`. Выполняется настоящий `mods/aic_body/main.lua` и его модули в Lua 5.4 через Lupa. Тестовый EMF возвращает отражённые поля, обрабатывает события/удаления на следующих шагах и позволяет моделировать отказы. Это проверяет наш код и wire-контракт, не движок Enshrouded, ABI reflection или графическую модель.

Покрываются:

- отсутствие spawn при загрузке, status и diagnose;
- принятие запроса отдельно от подтверждённого guard/ready/health/proximity;
- спавн, stay-маркер, follow и отложенное удаление обоих объектов;
- повтор request ID, конфликт параметров, чужой профиль, неверные токены;
- смена сессии между preflight и запросом; hot reload; наблюдаемая подмена entity;
- смерть, отсутствие компонента, отказ spawn/destroy/записи lock, потерянное событие и таймаут;
- потеря соединения после исполнения запроса, неверная корреляция/JSON/версия;
- отказ CLI без разрешающего флага, неподходящий build, Cloud и чужой хост;
- постоянство личности и запрет её неявной перезаписи;
- состав архива, отсутствие runtime-данных, мод выключен по умолчанию.

## Ручные проверки после подтверждения

До теста выполнить [FIRST_RUN.md](FIRST_RUN.md), проверить backup, build, LOCAL-мир и LOCAL-персонажа. Выбрать ровное свободное место без врагов/важных построек. Не включать другие companion-моды.

| Шаг | Действие | Что записать / критерий |
|---|---|---|
| 1 | Diagnose и status | EMF/API/build, world/character slot и имя, epoch, mode absent, нет новых существ |
| 2 | Spawn с фиксированным request ID | Ровно один Vukah; faction 11, health >0, ready; guard на владельца; request succeeded либо точный код отказа |
| 3 | Повтор того же spawn ID | Тот же ответ, число существ не увеличилось |
| 4 | Игрок проходит 15–20 м по ровной поверхности | Тело действительно идёт, а не стоит/телепортируется; через follow фиксируется сближение; отдельно время и минимальная дистанция |
| 5 | Stay | Ровно одна бочка в месте тела; guard на неё; игрок отходит 15–20 м, тело остаётся в области маркера. Небольшое блуждание допустимо |
| 6 | Follow после Stay | Guard снова на игрока; тело подходит; бочка исчезает, `marker_id` отсутствует |
| 7 | Закрыть только Python-клиент и открыть status снова | Не появился дубликат; профиль UUID тот же, entity ID текущей сессии тот же |
| 8 | Dismiss | Запрос accepted до фактического исчезновения; затем succeeded, mode absent, тела и маркера нет, lock удалён |
| 9 | Новый spawn новым ID, затем dismiss | Тот же UUID личности; entity ID не обязан быть новым/прежним, от него личность не зависит |
| 10 | Перезагрузить мир только после полной очистки | Новый epoch, отсутствие автоматического spawn, старые request ID не исполняются в новой сессии |
| 11 | Проверить сохранение после нормального теста | После повторного открытия тестового мира нет забытой бочки/тела; сравнить с состоянием до теста |

Дополнительные испытания смерти, hot reload при живом теле, принудительного разрыва bridge и аварийного закрытия игры делать отдельно после успешных базовых шагов и нового backup. Они могут оставить объекты в save. Не убивать основного персонажа/процесс и не вызывать чужие консольные команды ради проверки.

## Критерий готовности этапа

Этап считается проверенным в игре только после воспроизведения spawn → реальное следование → stay → follow → dismiss и повторной загрузки тестового мира без остатков. Тестовый успех по fake EMF и `request.status=succeeded` при первом появлении не заменяют наблюдения реального движения.

При провале сохранить JSON diagnose/status, request ID, epoch, время, строки `[aic_body]` и связанные ошибки из `emf_core.log`. Если тело не удалилось, дальнейший spawn запрещён до выяснения причины/восстановления тестового мира. Не исправлять это случайным destroy по старому ID.
