## Что исправлено

Прежний `ground_unconfirmed` не позволял определить причину отказа и проверял только +X.
Теперь `controller.lua` создаёт восемь read-only Ground-запросов на окружности **радиусом 4 м**,
через 45°, начиная с +X. Это один радиус внутри требуемого диапазона 3–5 м, а не дополнительные
кольца или неограниченный перебор. Возвращённая позиция также обязана находиться на расстоянии 3–5 м.

Все Ground callbacks должны завершиться; затем направления рассматриваются в фиксированном порядке.
Для прошедшей Ground точки проверяется Wall, затем один асинхронный Path. При отказе этой точки
проверяется следующая. Первая точка, прошедшая все проверки, становится READY.
Нельзя одновременно иметь более восьми Ground или более одного Path; эти фазы не перекрываются.
Внутри одного поиска не более восьми Path-запросов. Другие направления не создают NPC.

Сохранены высотный предел 0.75 м, допустимый fog, запрет обнаруженной воды, Path с walk-only,
без прыжков/дверей/плавания, длиной до 8 м, точностью конца 0.5 м и прежними габаритами.
Игрок остаётся в пределах 0.25 м от начала поиска. Срок **20 с начинается с probe**, не с READY.
Python оставляет минимум 8 с на подтверждение и 2 с на отправку; поздний READY не продлевает срок.

`AIC_POSITION` в EMF log содержит отдельные записи `GROUND_ACCEPTED`, `GROUND`, `REJECT`,
`WALL`, `PATH`, `SELECTED` с номером поиска, probe nonce и номером направления.
Ground записывает requested X/Z, высоту игрока, фактические X/Y/Z, delta Y,
`api_ok`, `why`, `hop_y`, fog и water Y. NaN/Infinity сериализуются как строки.
При `ok=false` Lua binding отдаёт Y=0: это помечено `ground_y_measured=false` и **не считается
измеренной высотой поверхности**. Значение delta в такой записи тоже не доказывает реальный перепад.

| Причина | Значение |
| --- | --- |
| `ground_request_refused` | API не принял запрос; конкретная внутренняя причина не выдумывается |
| `ground_api_not_ok` | Callback сообщил отказ; исходный `why` сохранён |
| `ground_invalid_coordinates` / `ground_xz_mismatch` | Недостоверные координаты / ответ для другой точки |
| `ground_height_delta` / `ground_distance` | Превышен допустимый перепад / расстояние |
| `ground_fog_unknown` / `ground_fog_unsafe` / `ground_water_present` | Не пройдены проверки окружения |
| `building_obstruction` | Wall обнаружил препятствие |
| `path_refused`, `path_invalid_result`, `path_not_found`, `path_not_reaching` | Отказ Path или недостоверный результат |
| `path_count`, `path_length`, `path_non_walk`, `path_endpoint` | Нарушен контракт безопасного пути |
| `no_safe_candidate` | Все восемь направлений отвергнуты; детали в отдельных записях |
| `search_timeout`, `queries_pending` | Срок закончился / предыдущие запросы ещё не завершены |
| `ground_api_error_pending_unknown`, `path_api_error_pending_unknown` | Исключение при отправке; принятие запроса неизвестно |

Вывод: несколько **ожидающих** Ground-запросов поддержаны. Это не утверждение о параллельном
выполнении игровых операций на CPU-потоках. В нашем моде предел снижен до восьми.
Подтверждённого cancel Ground API нет: timeout не обнуляет pending. Если callbacks не приходят,
следующий поиск блокируется. Исключение после возможной отправки также оставляет pending неизвестным.
При reload/паузе Lua ответ может быть потерян; незакрытый Python-журнал в этом случае не сбрасывается.

## Поиск, подтверждение и повтор

Новый `scripts/smart_spawn_position.py` имеет три явно выбираемых режима:

- `--search-only`: probe и ожидание READY; никаких подтверждений или spawn.
- `--interactive`: prepare, wait, локальное Y/N/ESC и единственный возможный spawn в одном процессе.
- `--settle-only`: только read-only status и закрытие завершённого журнала поиска. Нового probe нет.

Локальный клавиатурный механизм Stage 10.11.2 сохранён: без Enter, очистка буфера до/после READY,
проверка отпускания клавиш, игнорирование ранней/удержанной Y, отмена N/ESC/deadline.
Чат не используется для передачи разрешения. Режим search-only не оставляет разрешения на будущий spawn:
для интерактивного запуска потребуется новый поиск и свежая Y.

`SmartPositionClient` хранит каждый поиск в `smart-searches/000001`, `000002`, … рядом со старыми
журналами. Директория создаётся эксклюзивно. Закрытие допустимо только для READY/STOPPED,
pending=0, attempted=false, recoverable=true, того же probe/session, отсутствующего общего
`spawn-intent.json` и неизменного UNUSED latch. `closed.json` фиксирует хеши всех файлов поиска.
Новый поиск — только новая явная команда после проверки закрытых историй. Автоматического цикла нет.
Все 75 прежних файлов трёх probes pinned отдельно; их изменение блокирует работу.

Если очередь не завершена, CLI не закрывает журнал и сообщает блокировку. Позже оператор может
явно выполнить `--settle-only`; при несовпадении сессии, reload, неизвестном результате или повреждении
истории требуется отдельный разбор. Никакого удаления истории, очистки latch или обхода intent нет.

Перед spawn повторно проверяются текущий LOCAL context/PID/player, session, выбранный probe,
точное совпадение координат с показанным READY, отсутствие pending/attempted,
срок и UNUSED latch; Lua повторяет проверку смещения игрока, существующего NPC и Wall.
Ground/Path подтверждены только в пределах текущего 20-секундного окна, это не непрерывная проверка
изменений ландшафта. Python пишет общий fsynced intent **до отправки**; Lua меняет latch **до native spawn**.
Любой исход после intent, включая таймаут, потерю ответа и нулевой entityId, запрещает повтор.
Ни `destroy`, ни автоматическое восстановление/rollback не добавлены.

## Ограничения, которые офлайн не устранить

Реальная скорость восьми Ground callbacks, нагрузка на server step, доступность ground/fog,
места на выбранном кольце и задержка Path в этой сборке ещё не измерены. Ожидание всех callbacks
может оставить слишком мало времени для Y: безопасный исход — отмена, не продление deadline.
Кольцо 4 м не гарантирует нахождение любой возможной точки в окружности; безопасной точки может не быть.
Wall/path clearance не доказывают отсутствие всех коллизий, мелкой воды и динамических препятствий.
Визуальный humanoid render, мирное поведение, сохранение/удаление NPC и надёжный generation ID
не подтверждены этим этапом. Native API и Lua latch не дают гарантии от сбоя питания.
После reload с потерянными callbacks требуется разбор, а не сброс pending/истории.
Старый отказ `ground_unconfirmed` ретроспективно уточнить нельзя: нужных полей в старом логе нет.
