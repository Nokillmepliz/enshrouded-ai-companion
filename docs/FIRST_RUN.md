# Первый запуск: подготовка и отдельный игровой этап

После технического ревью использовать **safety_revision=2**, 87 тестов и текущий SHA-256 из [TEST_RESULTS.md](TEST_RESULTS.md). В recovery разрешён только явный безопасный dismiss для сохранённых handle; неподтверждённые объекты не удаляются, смена сессии не снимает старый lock. Подробный актуальный порядок — [PROTOCOL.md](PROTOCOL.md#runtime-lock-и-безопасное-восстановление); он заменяет старые указания об общем запрете dismiss в recovery и rollback без fingerprint.

Для этой Windows-машины подготовлен [отчёт этапа 3 с точными путями, совместимостью и командами](STAGE3_PREFLIGHT.md). Он дополняет общий порядок ниже; новые результаты — 56 тестов и архив с журналированием.

**Сейчас выполнена только подготовка в каталоге проекта. Установка, изменение конфигурации EMF, запуск игры и все команды тела ниже предназначены для отдельного этапа после подтверждения пользователя.**

## 1. Что можно проверить без игры

Нужен Python 3.12 x64. Runtime-клиент использует стандартную библиотеку; `lupa==2.6` нужен только разработчику для тестов Lua 5.4.

```powershell
py -3.12 -m venv .venv
$Python = '.\.venv\Scripts\python.exe'
& $Python -m pip install -r requirements-test.txt
& $Python -m unittest discover -s tests -v
& $Python scripts/package.py
& $Python -m companion profile-init --name "Спутник"
& $Python -m companion --help
```

Если `py -3.12` отсутствует, использовать абсолютный путь к установленному Python 3.12. Для уже подготовленного рабочего каталога доступен `$Python = '.\.tools\python\python.exe'`; он не входит в Git и не является требованием проекта. Его Python взят из [официального embeddable package 3.12.10](https://www.python.org/downloads/release/python-31210/), тестовая Lua — [Lupa 2.6](https://pypi.org/project/lupa/2.6/). Системная установка при подготовке не менялась.

Результат упаковки — `dist/aic_body-0.1.0.zip` и SHA-256. В архиве ровно `mod.json`, `main.lua`, `body.lua`, `json.lua` внутри `aic_body/`. Личных данных, runtime lock и установщика нет; `enabled=false`.

Профиль создаётся один раз в `runtime/personality.json`. Скопировать его вместе с резервными копиями проекта; не помещать в каталог игры. Удаление/замена профиля создаст другую личность, но не удалит старое тело.

## 2. Перед разрешённой установкой — резервная копия

1. Зафиксировать версию/номер сборки Enshrouded, путь к игре и список существующих модов/загрузчиков. Клиент прототипа допускает только исследованную сборку **1273043**. При другой сборке остановить игровой этап и исследовать совместимость, не снимать проверку флага вручную.
2. Закрыть игру и выделенный сервер, дождаться завершения синхронизации Steam. Не копировать активно изменяемые сохранения.
3. В отдельный каталог вне игры, с датой и временем, скопировать полностью локальные сохранения, Steam Cloud-копию нужного Steam-аккаунта и текущую мод-конфигурацию. Пути из [upstream docs/saves.md](https://github.com/matenm/emf-enshrouded/blob/08d600155fcadc8e45cc9c6f3932a67c717345be/docs/saves.md):
   - локальные: `%USERPROFILE%\Saved Games\keen games\Enshrouded\default\`, также `local_settings.json` на уровень выше;
   - Steam: `<Steam>\userdata\<account>\1203620\remote\`;
   - моды/настройки: существующая `<game>\emf\` и файлы других загрузчиков, если они есть;
   - личность: `<project>\runtime\personality.json`, если уже создана.
4. Проверить, что копия содержит файлы и читается; записать SHA-256 файлов исходников и копии, сравнить. Отсутствующий путь не считать успешно сохранённым: найти фактическое место хранения. Сохранить комплект персонаж + `global.ksd` + мир совместно.
5. Автоматический backup EMF — дополнительная мера, а не замена проверенной копии до установки. Dedicated server в этот прототип не входит; EMF не обещает резервировать его `savegame`.

Эти действия сейчас не выполнялись. Подготовка к тесту не требует изменять или переносить основной мир.

## 3. Установка после подтверждения

1. Установить проверенный релиз **EMF 0.3.2** из источника, указанного в [upstream README](https://github.com/matenm/emf-enshrouded/blob/08d600155fcadc8e45cc9c6f3932a67c717345be/README.md). Не заменять существующие загрузчики вслепую. Этот репозиторий EMF не устанавливает и игру не патчит.
2. Убедиться в наличии Lua Scripts host **1.8 или выше** (в исследованном EMF — 1.9), совместимого с API 20.
3. При закрытой игре распаковать `dist/aic_body-0.1.0.zip` в `<game>\emf\mods\`. Должно получиться `<game>\emf\mods\aic_body\mod.json`, без лишнего уровня папок. Не копировать `.research`, тесты, Python или `runtime.lock`.
4. Разрешённым изменением `<game>\emf\config\aic_body.ini` включить только адаптер:

   ```ini
   [aic_body]
   enabled=1
   ```

   Если файл существует, сохранить его копию и отредактировать нужную секцию, а не перезаписывать весь файл. Штатный Companion, pet_follow, beastmaster и другие управляющие существами моды на время теста выключить; изменения их конфигурации также входят только в согласованный этап.
5. В существующий `<game>\emf\emf_core.ini` добавить/изменить секцию, сохранив остальные настройки:

   ```ini
   [debug]
   bridge=1
   ```

6. Перезапустить игру вручную. Новые объявления событий должны быть зарегистрированы при старте. Создать/выбрать **отдельного LOCAL персонажа и LOCAL мир** для проверки. Не выбирать основной персонаж или Steam Cloud-мир.
7. Ничего автоматически не появится. В консоли EMF `mods`/`lua.status` должны показать загрузку `lua` и `aic_body`; ошибки есть в `<game>\emf\emf_core.log`.

Игра сама сохраняет загруженный мир. Даже без явного вызова сохранения игровой тест может изменить тестовый save; поэтому резервная копия обязательна перед этим этапом.

## 4. Диагностика подключения без спавна

В PowerShell из корня проекта, с уже выбранным `$Python`:

```powershell
$Game = 'D:\SteamLibrary\steamapps\common\Enshrouded' # заменить фактическим путём
& $Python -m companion diagnose --game $Game
& $Python -m companion status --game $Game
```

Можно вместо `--game` указать `--pid` конкретного процесса. Клиент использует upstream-проверку владельца named pipe и никогда не запускает игру. Не повышать привилегии игры без необходимости: bridge требует того же Windows-пользователя и подходящего integrity level.

Проверить `hello.emf=0.3.2`, `api=20`, `protocol=1`, `game_build=1273043`, `process=client`. В `game` должны быть `world.kind=server`, `world.status=running`, локальный world slot 1–10, `character.storage=local`, ожидаемые `character.slot` и `character.name`. У `body.state` — `mode=absent`, `recovery_required=false`.

`diagnose` может успешно вернуть данные bridge и одновременно `body_error`: это значит, что тело ещё не готово к командам. В главном меню status мода недоступен, поскольку EMF исполняет его только в мире хоста.

## 5. Первая последовательность команд — только после разрешения

Значения ниже — пример. Подставить **фактически проверенные** slot/имя из diagnose, не копировать номера наугад. Пример использует world slot 1 и character slot 2 с именем `Body Test`.

```powershell
$TestArgs = @('--game', $Game, '--allow-game-mutations', '--world-slot', '1',
              '--character-slot', '2', '--character-name', 'Body Test')

& $Python -m companion spawn @TestArgs --request-id spawn-001
& $Python -m companion status --game $Game
& $Python -m companion follow @TestArgs --request-id follow-001
& $Python -m companion stay @TestArgs --request-id stay-001
& $Python -m companion follow @TestArgs --request-id follow-002
& $Python -m companion dismiss @TestArgs --request-id dismiss-001
```

Выполнять по одной команде, осматривая результат по [TEST_PLAN.md](TEST_PLAN.md). Не запускать всю последовательность одним блоком без наблюдения. `spawn` уже устанавливает follow. `stay` создаёт бочку в месте тела. После `follow` и возврата тела старый маркер удаляется; после `dismiss` проверить исчезновение обоих.

Каждая новая операция получает новый request ID. Повтор того же ID означает повторное получение исходного результата, а не новую команду. При потерянном ответе:

```powershell
& $Python -m companion status --game $Game --request-id spawn-001
```

Не повторять spawn новым ID, пока статус неизвестен. `succeeded` — проверенные наблюдения, `accepted` — процесс проверки ещё идёт. CLI возвращает код 1 при отказе/таймауте; детали печатает JSON в stderr. Потеря клиента не отменяет уже включённое штатное поведение сущности.

## 6. Ошибки и завершение

| Код / симптом | Действие |
|---|---|
| Нет соединения | Проверить игру, правильный game/PID, `[debug] bridge=1`, `emf/bridge.txt`, пользователя/уровень прав и лог EMF |
| `console_refused` / нет ответа адаптера | Проверить загрузку `lua`/`aic_body`, enabled, зависимости и загруженный локальный мир |
| `unsupported_game_build_or_process` / `unsupported_emf` | Остановить тест; вернуться к проверке совместимости |
| `wrong_test_world` / `wrong_test_character` | Сверить actual state и выбранный выделенный LOCAL мир/персонажа |
| `stale_epoch` / `session_or_adapter_changed` | Получить status новой сессии; старые entity ID больше не использовать |
| `verification_timeout_outcome_unknown` | Прочитать status по request ID и лог. Запрос мог исполниться. Не делать новый spawn вслепую |
| `verification_timeout` | Проверка контроллера не завершилась. Сохранить диагностику; отдельно вызвать dismiss, если идентичность тела известна |
| `recovery_required` / `identity_changed` | Читать recovery_action. Для сохранённых handle возможен новый dismiss ID; неподтверждённые сущности не удалять. При потере владения — согласованное восстановление, без ручного снятия lock |
| `fingerprint_missing` / `marker_fingerprint_missing` | ID сохранён без доверия, автоматического rollback нет. Dismiss может только наблюдать отсутствие этого ID; остановить испытание для анализа/восстановления |
| `destroy_refused` / `destroy_outcome_unknown` / `cleanup_timeout` | Эффект может быть частичным. Новый dismiss продолжает наблюдение без повторного destroy для уже затронутого объекта; если он не исчезает, согласовать восстановление |

Перед нормальным выходом выполнить dismiss и проверить `mode=absent`, отсутствие `entity_id`/`marker_id` и бочки в мире. Только потом закрыть игру. Не редактировать Lua-файлы и не выключать мод при живом теле: hot reload теряет runtime handles и потребует восстановления тестовой среды.

После завершения выключить адаптер через его ini и, при необходимости, bridge — при закрытой игре. Это изменения отдельного игрового этапа. Восстановление: сначала сохранить копию текущего тестового состояния для диагностики, затем при закрытой игре вернуть согласованный комплект файлов из backup. Основные/Cloud-сохранения не восстанавливать без отдельной необходимости и согласия. Удаление мода само по себе не удаляет уже сохранённый маркер.
